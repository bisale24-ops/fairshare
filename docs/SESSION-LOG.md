Проект: Fairshare, кейс 6 «Совместные расходы» (тестовое задание Mad Devs). Репозиторий: https://github.com/bisale24-ops/fairshare

**Инструмент:** Claude Code (CLI), модель Claude Sonnet 5.5. Агент читает и пишет код, запускает тесты, браузер, Docker и git; я ставлю задачи,
принимаю решения и получаю отчёты.

## Как читать этот документ

- **Это описание работы, а не стенограмма чата.** Задачи (раздел 1) изложены от первого лица в деловой формулировке: что я поручил и что получил в результате.
- **Время и хеши** (раздел 2) взяты из `git log`: любую строку можно проверить командой `git show <хеш>`.
- **Сырой экспорт сессии не публикуется.** Та же сессия содержит посторонние личные материалы (почта, переписка по другим делам). Вместо него: задачи, хронология по коммитам, решения, ошибки агента и подтверждения проверок. Фрагменты исходной сессии по запросу.
- Остальные документы: `DEVLOG.md` (технический журнал по шагам), `docs/PROMPTS.md` (кто что решал), `README.md` (устройство, доказательства, ограничения).

## 3. Основные решения и обоснование

1. **Деньги — целые числа в минимальных единицах валюты.** Дробных чисел нет нигде; число знаков зависит от валюты (иена 0, динар 3). Остаток при делении всегда отдаётся одним правилом (наибольший остаток, затем меньший id).
2. **Баланс не хранится, а считается из строк.** Правка или удаление старого расхода не может оставить устаревшие суммы; сумма балансов группы всегда равна нулю.
3. **Минимальный набор переводов** считается точно до 12 человек (подмножества, O(3^n)), дальше — жадно; результат кэшируется.
4. **Платёж засчитывается после подтверждения другой стороной**; закрытая группа заморожена, чтобы итоговое письмо оставалось верным.
5. **Живые обновления через Server-Sent Events**, одним процессом (в памяти). Масштабирование описано (LISTEN/NOTIFY).
6. **Сбои учтены в архитектуре:** все записи атомарны под блокировкой группы; создание расхода и платежа защищено ключом идемпотентности, хранящимся в той же транзакции; nginx заново узнаёт адрес API и быстро отказывает; клиент переподключает поток.
7. **Проверка кода независимыми агентами-ревьюерами**, каждый вывод проверен чтением кода до исправления; найденное закреплено тестами.
8. **Осознанные компромиссы** (в README): токен в `sessionStorage` (две вкладки = два пользователя), почта-заглушка без подтверждения адресов.

## 5. Подтверждения

- **Тесты:** 81 в бэкенде (покрытие строк 95 %), 31 во фронтенде (покрытие строк 42 %; страницы целиком проверяются браузерными сценариями).
- **Браузерные сценарии (6):** два пользователя; исправления ревью; членство и платёж наличными; мобильная вёрстка 375 px; убийство контейнера API при работающих пользователях; автоперезапуск процесса.
- **Мутационная проверка:** осознанно ломались логика остатка, учёт платежей, ранний коммит транзакции, проверка прав, проверка версии, защита от дубля, точечное обновление экранов. Все поведенческие поломки пойманы; один «мутант» эквивалентный и объяснён.
- **Нагрузка:** 30 запусков из 30 при параллельном выполнении трёх сценариев; замеры времени ответа в README (вид группы 25 мс, баланс по всем группам 66 мс на 300 расходах).
- **CI на GitHub:** первый запуск — ошибка в тесте (исправлена); последующие — успешны. Ссылки: https://github.com/bisale24-ops/fairshare/actions/runs/37844602114 (красный), https://github.com/bisale24-ops/fairshare/actions/runs/37844981668 (зелёный).
- **Docker Compose** проверен локально командой `docker compose up --build --wait` и на машинах GitHub.

## 6. Границы проверки

- Код написан агентом. Я ставил задачи, принимал решения (выбор кейса, срок, публикация, что исправлять) и получал отчёты по результатам. Построчного разбора кода я не выполнял; уверенность в результате опирается на тесты, независимое ревью агентами, браузерные сценарии и CI.
- Не проверялось: падение самого сервера БД посреди записи, нагрузочное тестирование, реальная отправка почты (транспорт — заглушка).
- Остальные известные ограничения перечислены в разделе «Honest status» файла `README.md`.
